# v0.4.0 Travel Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the already verified 2020–2025 source corpus and application changes into one coherent, signed, clean-install v0.4.0 APK with an independently verified SHA-256 digest.

**Architecture:** An explicit release manifest selects six completed sets from the longer 1962–2025 archive. A release builder renders those sets and constructs the normalized SQLite database entirely in an ignored staging directory, validates assets and database together, then performs one rollback-safe publication into Android assets. A package auditor reads the final APK itself—not the workspace—to verify identity, schema, counts, hashes, local dependencies, permissions, and excluded source material before the artifact is handed off.

**Tech Stack:** Node.js 22, JSON Schema/Ajv, Python 3/SQLite/ZIP inspection, Kotlin 2.4, Gradle/Android build tools, PowerShell, `aapt2`, `apksigner`, SHA-256.

**Spec:** `docs/superpowers/specs/2026-10-08-library-topic-search-and-travel-release-design.md`

## Global Constraints

- This plan runs only after the notebook-polish, generic-library/topic-filter, and 2020–2025-curation plans pass and are committed.
- The long-term archive continues to target 1962–2025. The travel release selects exactly `putnam/2020` through `putnam/2025`; unselected source sets must neither block nor leak into it.
- Release manifest version is 1, content schema version is 3, content version is `putnam-2020-2025.1`, release ID is `putnam-2020-2025-v0.4.0`, app version name is `0.4.0`, and app version code is `4`.
- Generated paths are `content/{collectionId}/{setId}/...` plus one deduplicated `content/shared/...`; all document links and hashes are calculated after final placement.
- Assets and database are validated in staging before either replaces the packaged baseline. Publication is rollback-safe and never leaves a known assets/database mismatch.
- The final APK contains rendered HTML/CSS/fonts/approved local figures and the immutable database; it contains no original PDFs, source TeX, source review notes, network fallback, or `android.permission.INTERNET`.
- Development progress and notebooks are disposable. Delivery is a clean install; no migration or `adb install -r` promise is added.
- Use the existing local signing setup without reading, printing, copying, or committing secrets. The retained signer certificate SHA-256 is `f9e07df7b54ed8f3c893303d4724a5387eec18d6bc14f7ed774e8240a2822a23`.
- Invoke the release APK assembly only after every source, tooling, application, signing-preflight, and available device gate passes. The intended final path is `dist/putnam-workbook-2020-2025-v0.4.0.apk` with adjacent `.sha256`.
- Do not add `Co-Authored-By` trailers.

## Review Focus

- A subset builder that silently packages an extra completed/source set or omits one selected set defeats progressive release isolation (Tasks 1–2).
- Publishing fresh HTML beside a stale SQLite DB, or vice versa, can pass shallow workspace checks while the app opens the wrong content (Task 2).
- A verifier that reads working-tree manifests instead of ZIP entries can approve a stale or tampered APK (Task 3).
- Missing transitive CSS/font/figure files, wrong generic-directory relative paths, orphan topic joins, and metadata/count drift must fail before assembly and again from the APK bytes (Tasks 2–4).
- The final app must be a clean-install v0.4.0 signed by the retained certificate, contain no Internet permission/PDF/TeX source, and expose exactly six sets and 72 problems (Task 4).
